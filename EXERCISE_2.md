**Questions** (depend on the tasks above)

- [x] What problem does a package manager actually solve that "download the library and put it in a folder yourself" doesn't? Be specific.

A package manager automatically installs and tracks the libraries and tools a project depends on, including their versions and dependencies. This makes it much easier for everyone working on the project to install the same required packages instead of manually downloading and managing files.

- [x] What's the difference between `dependencies` and `devDependencies` in `package.json`? Which category will Vite, your linter/formatter, and TypeScript belong to, and why?

dependencies are packages needed for the application itself to run, while devDependencies are tools needed only during development or building. A lockfile such as package-lock.json records the exact versions of installed packages and their dependency tree. On a larger project, pnpm can save disk space and installation time by keeping packages in a shared content-addressable store and linking them into projects instead of storing separate copies everywhere. npm is more conventional and straightforward, while pnpm's node_modules structure is different and can occasionally expose packages that incorrectly assume npm-style dependency layouts.

  3. The `Location | string` ambiguity in [js/views/timeline.ts](js/views/timeline.ts): the code was trying to build a label from either a full `Location` object or a plain ID string, and TypeScript correctly rejected that mismatch. This was a real design ambiguity, not pedantic behavior. The app was blending two representations of the same concept, and the fix was to normalize everything to a plain string label before rendering.

  4. Missing `bookmarked` on the `Evidence` model in [js/types.ts](js/types.ts): the runtime code was setting `ev.bookmarked = true/false`, but the type model did not include that field. This was not compiler noise; it was a real domain-model gap. The app was relying on a property that the data contract never declared, so TypeScript correctly forced us to model it explicitly.

  5. Missing custom `window` properties in [js/app.ts](js/app.ts): TypeScript complained that `window.navigateTo` and `window.handleSortChange` did not exist unless we declared them. This was mostly a real integration contract issue rather than an application bug: the app was attaching globals to the browser window without telling TypeScript about them. It is a valid type issue, but it was not pointing to a runtime logic bug in the case logic itself.

  Overall, the strongest examples were the nullable DOM access, the event-target narrowing, and the missing `bookmarked`/union-shape model. Those were genuine latent issues. The custom `window` globals were more of a contract declaration problem than a latent bug.
